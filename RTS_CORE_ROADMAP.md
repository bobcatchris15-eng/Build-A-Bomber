# Build-A-Bomber: RTS Core Roadmap (terrain, maps, base building, production)

**Status (2026-07-25): A1, A2, B1, B2, B3, B4, and B5 landed; everything else
is planning only.** This is a resumable roadmap, written so a fresh session can
pick up any single chunk without re-deriving the architecture. Chunks are
ordered with explicit dependencies in the sequencing table at the end; each is
sized to land as one commit with its own `PROGRESS.md` entry. **Update the
sequencing table's status as chunks land** — a stale "next up" header in a plan
doc is exactly the confusion that `LOCOMOTION_REBUILD_PLAN.md` accumulated
before being corrected on 2026-07-24. **Next up: B6** (retire `elevation_zones`,
migrate all 8 maps onto heightmaps, rect + bounds).

**B5 deviation from this doc's literal text, logged here so it isn't mistaken
for an oversight:** B5's bullets say to delete `_near_elevation_zone()` and
stop the navmesh source geometry from being flat, unconditionally. Actually
doing that before B6 migrates real maps off `elevation_zones` would break
`highland_chokepoint`/`twin_summits` today - `_near_elevation_zone()` exists
specifically to keep noise from creating a seam against their ramps, and
`_build_ground_faces()`'s own header comment documents *why* the navmesh
source stays flat for that system (10+ second Recast bakes, broken ramp
connectivity). Neither regression applies to an O(1) heightmap image lookup
with no discrete ramp geometry, so B5 landed the slope-rejecting real-height
navmesh **flag-gated on `terrain.heightmap` being set** (same pattern as B4) -
zero risk to the 8 existing maps, genuinely real for whichever map B6 migrates
first. `_near_elevation_zone()` itself gets deleted for real in B6, once
nothing depends on it anymore.

Reference implementation for all of this is OpenRA, cloned locally to
`C:\Misc\openra` (not vendored into this repo). Specific `file:line` citations
throughout point into that checkout.

## Context

The game's *distinctive* system — the unit designer — is well developed. The RTS
layer it feeds into is not. Chris asked to bring **maps, base building, and unit
production queues** to "bog-standard RTS" quality, using OpenRA (cloned to
`C:\Misc\openra`) as the reference for what a player expects, and separately
called out that the maps themselves are "functional, but very small and sparse,
with no real terrain features."

Four things drive this roadmap:

1. **Terrain is effectively flat and blocky.** `GROUND_NOISE_AMPLITUDE = 0.4`
   (`terrain_builder.gd:94`) is a barely-visible ripple. Real elevation is authored
   as `elevation_zones` — an axis-aligned rect plateau plus *one* ramp on a chosen
   side (`terrain_builder.gd:1114-1125`) — which cannot express cliffs, ravines,
   valleys, or escarpments at all. A richer `hills` primitive exists
   (`:111`, `:190`) but **no map uses it**.
2. **Height differences are visible but not *effective*.** The navmesh source
   geometry is deliberately flat at y=0 (`_build_ground_faces:429`), so slope never
   gates pathing — a cliff is walkable. `MAX_WALKABLE_SLOPE = 0.7` (`:96`) exists
   but is only consulted in `is_position_blocked` when `hills` is non-empty
   (`:1171`), i.e. it is dead code today.
3. **Units drive through buildings.** `battle_unit.gd:143` sets
   `collision_mask = 1`; buildings are on layer 8 (`building.gd:101`). The navmesh
   bakes once (`skirmish.gd:688`) and never rebuilds. Weapons *do* check layer 8
   (`auto_weapon.gd:277`) — buildings block line-of-fire but not movement. That
   asymmetry marks it as an oversight, not a design choice.
4. **The production path is implemented three times.** `skirmish.gd:1074`
   `_queue_player_unit`, `enemy_ai.gd:133` `_queue_entry`, and `enemy_ai.gd:168`
   `_ensure_harvester` each re-do the same six steps. Every queue feature below
   would otherwise be built 3×.

### Decisions already made (asked and answered)

- Content moves to **JSON data files**, one decision covering maps *and*
  `HULL_MODDING_PLAN.md`'s unanswered schema questions.
- **N-player is a real goal**, prioritized.
- The **terrain/maps track comes first**, after the mandatory production refactor.
- **`INFINITE_PLAYER_RESOURCES_FOR_TESTING` stays ON by default** — the game is
  still heavily in development. It becomes a *runtime toggle in a debug/options
  menu*, not a flipped default.
- A **full refactor of the map foundation is acceptable**, including pulling in
  another language.

### On "another language"

Taken as permission for the **authoring/generation pipeline**, not the runtime.
Runtime stays GDScript — it has to, since `terrain_height_at()` is queried by every
unit every physics tick. But terrain *generation* moves to **Python**, which this
project already has strong precedent for: every hull and part mesh is generated by
`tools/blender/build_meshes.py` and the resulting `.glb` is a committed,
regenerable artifact. Terrain gets the same relationship.

## D1 — The content-format decision (settle once, applies to maps and hulls)

`HULL_MODDING_PLAN.md` §5 has six open questions that are the same questions maps
raise. Answer them once:

- **Format: JSON**, via Godot's native `JSON` class. Precedent exists — blueprints
  are already JSON (`blueprint_manager.gd`, `prototype/data/loadout/`). No YAML
  dependency.
- **Versioning:** `"schema_version": 1` int on every content file.
- **Strictness by provenance, not file type.** Shipped content
  (`res://data/maps/`, later `res://data/hulls/`) → **hard-fail loudly** on unknown
  key, wrong type, or newer `schema_version`, matching the deliberately strict GLB
  `_part()` loader. User content (`user://blueprints/`, `user://maps/`) →
  warn-and-attempt, matching the existing `CURRENT_BLUEPRINT_VERSION` behavior.
- **Overrides (§5 Q5):** `res://data/maps/` built-in, `user://maps/` user. Same
  `id` in both → user wins, logged loudly.
- **Unknown-id fallback (fixes §5 Q4):** must be shape-appropriate. Today
  `module_catalog.gd:1571` returns `basic_cannon` for an unknown *hull*.
- **Validation** = OpenRA's ~40 lint passes reduced to the GDScript analogue: *one
  reflective test over the whole content corpus*, driven by a declarative field
  spec — not hand-written per-field asserts.

## Phase A — Foundation (first, in this order)

### A1. One production authority — *afternoon, blocks everything*

**Goal:** exactly one code path enqueues, ticks, and spawns units.

New `prototype/scripts/production_queue.gd` (`RefCounted`, owned by `skirmish`),
keyed `queues[team][tier]` (light/medium/heavy).

**Adopt OpenRA's `ClassicProductionQueue` model, not the per-factory model.** In RA
the queue lives on the *player*, one per category, and extra factories add
**speed, not parallelism**. Right fit here because this game's "category" already
*is* hull weight tier (`module_catalog.gd:1267 get_hull_size_tier`, thresholds
150/400), and tier maps 1:1 to a building kind. It also kills the least-busy hack
in `get_team_factory` (`skirmish.gd:856`), gives the HUD three queues instead of
N-buildings-worth, and lets player and AI share one object.

Move in: tier resolve, `validate_build_legality`, cost, `build_time_for_cost`
(`skirmish.gd:643`), faction multiplier, plus the tick loop and `queue_unit` from
`building.gd:316-326`. `building.gd` keeps only `_spawn_unit` (as
`spawn_from_queue`) and its `Label3D`, now reading from the queue.
`get_team_factory` becomes `has_factory_of_tier()` / `factories_of_tier()`.
Then `enemy_ai.gd:133` and `:168` both collapse to
`skirmish.production.enqueue(team, blueprint, 1)`.

> **Write every function `team`-parameterized, never `PLAYER_TEAM`-hardcoded** —
> this is what keeps B2's slots refactor a storage swap instead of a rewrite.
> `can_afford`/`spend`/`add_resources` (`skirmish.gd:657-674`) are *already*
> team-parameterized: that's the stable seam, so A1 and B2 don't collide.

**Verify:** 113 existing tests unchanged. One new test enqueues as both player and
AI (via `enemy_ai._try_produce()`), asserting both landed in the same queue object
and produced real units. Pure refactor — no screenshot needed.

### A2. Debug/options menu for dev toggles — *small*

`INFINITE_PLAYER_RESOURCES_FOR_TESTING` (`skirmish.gd:654`, used at `:184`, `:665`)
goes from `const` to a runtime `var`, **default still `true`**, surfaced in a real
debug/options panel alongside other dev switches worth having (reveal-all-fog,
instant-build, spawn-unit). Do **not** flip the default — Chris is still developing
against it.

The test-suite value comes from it being *settable*: economy tests (D1) explicitly
turn it off for their own run, so drip-feed and refund behavior is genuinely
exercised while normal play keeps the sandbox.

**Verify:** a test sets it false, asserts `spend()` fails at zero; sets it true,
asserts the top-up path still works.

## Phase B — Terrain foundation + maps as data *(the prioritized track)*

The through-line: **retire the rect-soup elevation model in favour of a real
heightfield**, make slope actually gate movement, and add a Python authoring
pipeline so richer/bigger maps are cheap to produce.

This is less invasive than it sounds because the seams already exist:
`terrain_height_at(map_def, pos)` (`:1112`) is the single gameplay-Y query, and
`height_at(map_def, x, z)` (`:186`) is already the "continuous elevation" layer
beneath it. `build_ground_visual_mesh` (`:706`) already builds a real subdivided
heightmap mesh from `height_at()`. The refactor swaps implementations behind those
seams rather than rewriting callers.

### B1. Map schema validator — *afternoon, no format change*

Add `MapCatalog.FIELD_SPEC` (declarative: field → type → required subkeys → range)
and `MapCatalog.validate_map(id) -> Array[String]`. One new test walks all 8 maps
asserting zero errors, **including unknown-key detection**.

Pure insurance, and it builds the machinery B3 needs. Ship before touching the
format so the extraction has a safety net.

**Verify:** catches a deliberately corrupted in-memory copy — bad
`map_half_extents` type, misspelled `elevaton_zones`, resource node out of bounds.

### B2. 2-team dicts → slots array — *one session*

**Goal:** N players representable; runtime still spawns 2.

Less invasive than it looks — `can_afford`/`spend`/`add_resources`/
`is_energy_deficit`/`get_team_units`/`get_team_buildings` are already
`team`-parameterized. Real hardcodings: `skirmish.gd:17-18` (consts), `:21-46`
(2-entry `economy`/`energy_pool` literals), `:178-186`, `:236`, `:238`/`:247`
(`player_hq`/`player_faction` ternaries), `:346` (win condition), `:665`,
`:766-802` (`_spawn_bases`), `:1202`/`:1204` (`_placement_validity`'s hardcoded
`PLAYER_TEAM`), plus `enemy_ai.gd`.

Introduce `slots: Array[Dictionary]` — `{team, faction, is_local, is_bot,
allies: Array[int], metal, crystal, energy, capacity, deficit, hq}`. Borrow the
worthwhile OpenRA `PlayerReference` fields (`Name, Faction, Team, Playable, Bot,
StartingUnitsClass, Spawn`, `Allies`); skip the rest. Keep `LOCAL_SLOT = 0` as a
named const so HUD and debug toggles stay honest. Replace `player_hq`/`enemy_hq`
with `slots[i].hq`, keeping thin properties so existing tests compile. Fog
(`:344-371`) becomes "visible to any slot allied with `LOCAL_SLOT`"; win condition
becomes "one alliance remains".

**Verify:** all 113 tests pass **untouched**. New test boots a 3-slot config (2v1
with an ally): allied repair works, fog reveals ally vision, resources independent.

**Risk:** widest blast radius of any chunk. Land it alone, nothing else in flight.

### B3. `const MAPS` → `res://data/maps/*.json` — *one session*

Delete the const (`map_catalog.gd:39-424`); `map_catalog.gd` becomes a
scan-and-cache loader running B1's validator at load (hard-fail per D1).

Schema v1: `player_start`/`enemy_start` → `spawns: [{id, hq, factory, refinery,
harvester}]`; add optional `players: [...]` (B2's slot fields), `markers: {name:
{position, kind}}` (OpenRA's named-map-actor idea without the actor/trait
machinery), and a **`terrain` block reserved for B4** (`{heightmap, surfacemap,
height_scale, features: [...]}`). Doing B2 first is what lets this be
`schema_version: 1` rather than needing v2 immediately.

**Verify:** behavior byte-identical — a test asserts the JSON-loaded
`lake_crossing` deep-equals a checked-in snapshot of the old dict; all 8 map smoke
tests pass unchanged; a hand-broken JSON hard-fails with a useful message.

**Risk:** the const is the *only* source of truth today, so a transcription error
is silent. The deep-equal test is the mitigation — not eyeballs.

### B4. Python terrain generator + heightmap-backed elevation — *multi-session, the keystone*

New `prototype/tools/terrain/build_terrain.py` (mirroring
`tools/blender/build_meshes.py`'s role; plain Python + numpy + Pillow, **no Blender
needed** — much simpler than the mesh pipeline).

- **Input:** the map JSON's `terrain.features` list — high-level, diffable,
  seeded primitives: `ridge`, `ravine`, `escarpment`, `hill`, `basin`, `plateau`,
  `cliff`, each with position/extent/height/falloff params.
- **Output:** `<map_id>_height.png` (16-bit grayscale) + `<map_id>_surface.png`
  (indexed palette → surface type), committed as regenerable artifacts exactly like
  `.glb` files.
- **Deterministic:** seeded, so regeneration is byte-identical — same property the
  mesh pipeline relies on for scoped commits.

Runtime: `height_at()` becomes a **bilinear sample** of the heightmap ×
`height_scale`; `get_surface_type_at()` becomes a nearest sample → palette index.

This is a **performance win, not just a fidelity one**. The existing code notes
`height_at()` is "genuinely expensive at scale (noise sample + hill/blob loops)"
(`:709`) and that per-vertex noise pushed a single navmesh bake from milliseconds
to 10+ seconds on a large map (`:380`). One texture fetch replaces all the loops —
which is exactly what makes B5's slope-aware navmesh and B7's bigger maps
affordable.

**Verify:** a test asserts the generator is deterministic (regenerate → identical
bytes), that a known ravine samples lower than its rim and a known escarpment
shows a slope above `MAX_WALKABLE_SLOPE`, and that bilinear sampling at
pixel centres matches the source PNG exactly. Screenshots of each feature type.

**Risks:** bilinear sampling at map edges needs clamped addressing or units at the
boundary jitter. Keep the old analytic path behind a flag until every map is
migrated (B6) so this chunk can land without breaking un-migrated maps.

### B5. Slope-aware navmesh + terrain collision — *multi-session; needs B4*

This is what makes height **effective** rather than decorative.

- `_build_ground_faces` (`:390`) stops emitting flat y=0 quads: sample real height
  per corner, and **reject cells whose slope exceeds `MAX_WALKABLE_SLOPE`** — so a
  cliff or ravine wall becomes genuinely impassable, finally giving that constant a
  job. This is the analogue of OpenRA's hard `|Δheight| > 1` adjacency gate, which
  is independent of their terrain speed table.
- Give slopes real physics collision, retiring the documented "deliberately NOT
  physically-collidable ramps/plateaus" choice (`:22-27`) now that a continuous
  heightfield makes a single generated collision mesh straightforward.
- Delete the `_near_elevation_zone()` noise-suppression hack (`:167`) — it exists
  only to hide the seam between analytic rects and continuous height, which B4/B6
  removes.

**Risks:** this is the chunk most likely to break existing tests —
`test_terrain_builder_navmesh_ramp_connects` and the 8 per-map smoke tests all
assume the current flat-navmesh behavior. Expect to update them deliberately, and
be able to explain each change as intended rather than as a silenced failure.
Watch bake time; re-check it against the 10-second regression noted at `:380`.

### B6. Retire `elevation_zones`; migrate all maps; rectangular + bounds — *one session*

Convert each of the 8 maps' `elevation_zones` into `terrain.features` entries,
delete the rect plateau/ramp code paths (`_ramp_geometry`, `_ramp_quads`,
`RAMP_RUN_PER_HEIGHT`, `RAMP_PAD`, and the `elevation_zones` branches in
`terrain_height_at`/`is_position_blocked`/`_build_ground_faces`), and drop the
old analytic fallback flag from B4.

Also: `map_half_extents: float` → `Vector2` for non-square maps. Touch points:
`terrain_builder.gd:390-443`, `:706`, `:1112`, `skirmish.gd:416-418` (fog grid),
camera clamp, `scratch/capture_map.gd:33`. **Skip OpenRA's `MapSize` vs `Bounds`
duality** — their off-map cordon exists because tilesets need off-screen tiles;
this game has analytic ground. One rect.

Add the **missing map-bounds check** to `_placement_validity` (`skirmish.gd:1177`).
Note `is_position_blocked` reads `map_half_extents` (`:1156`) but only for ramp
geometry — it never actually bounds-checks.

### B7. Terrain type differentiation — *one session; needs B4*

The mechanism is already good and under-used: `TERRAIN_SPEED_MULTIPLIERS` in
`module_catalog.gd` gives real per-locomotor × per-surface speeds, but
`surface_zones` appears in **only one map** (`open_plains`). With B4's surface map
this becomes paint-not-rects.

Expand the roster beyond marsh/rocky/snow_mud/sand and make each read distinctly —
both visually (per-surface ground texture/tint, using the existing
`generate_terrain_textures.py`) and mechanically. Cross-check the multiplier table
against RA's own locomotor speeds (`mods/ra/rules/world.yaml:12-89`) as a balance
reference, keeping this game's 4-navmesh split as the locomotor abstraction.

**Verify:** the existing terrain-multiplier tests already prove real physics-tick
movement differences per locomotor — extend that pattern to each new surface.

### B8. Bigger, denser maps — *multi-session; content, not code*

With B4-B7 landed, author real maps: meaningful size increase, cliffs/ravines/
escarpments as actual tactical features, chokepoints created by terrain rather than
rock-cluster props, and high ground worth holding. Reuse the existing per-map smoke
test pattern (legal start points, resources reachable, HQs mutually reachable,
factory production works) plus B10's fairness lint.

**Risk:** this is the real time cost of the whole track, and it's authoring
judgment, not implementation. Budget it as its own arc; do one map end-to-end and
review before batching the rest.

### B9. Minimap — *one session + polish; needs B6*

**Not** render-to-texture — headless never rasterizes, which would make it
untestable. Reuse the existing world→cell `Image` mapping from
`_setup_fog_shroud`: bake a static terrain-colour `Image` once in
`_setup_navigation()` (now trivially sourced from B4's heightmap + surface map),
then per fog tick blit 2–3px blips for units/buildings/resources tinted by slot
colour, multiplied by the shroud alpha already being computed. Click-to-move-camera;
right-click-to-order in polish.

**Verify:** behavioral — a headless test reads pixels back and asserts an enemy
blip is absent while fog-hidden and present after reveal, and that a known water
region samples as water.

### B10. N-player spawn assignment + fairness lint — *multi-session; needs B3, B8*

Spawn markers come from B3. Adopt OpenRA's assignment verbatim: explicit pick >
**maximise summed squared distance to occupied spawns** when team-separation is on >
uniform random. That is genuinely their entire runtime fairness logic, ~15 lines.

Then **exceed OpenRA**, which validates only spawn counts/duplicates and has *no*
fairness lint. This project has a navmesh at bake time, so lint per spawn: HQ pad
legal, spawns mutually reachable on `ground_nav_map`, ≥N resource nodes within
radius R, pairwise spawn-distance variance under a threshold. Generalize the
existing `_smoke_test_map` helper to loop spawns. `match_setup.gd`/`map_select.gd`
grow a slot list + spawn picker.

## Phase C — Buildings are solid

### C1. Buildings block movement — *multi-session; highest-value non-terrain defect*

Do this **before** C4's exits — blocked-exit logic is meaningless while units phase
through walls. Two halves that must ship together:

1. `battle_unit.gd:143` `collision_mask = 1` → `1 | 8` (physics backstop, so a nav
   miss doesn't silently become a drive-through).
2. Dynamic navmesh. `NavigationObstacle3D` is a dead end — `battle_unit.gd:255`
   sets `avoidance_enabled = false`. Instead extend `_build_ground_faces` /
   `build_navmeshes` to accept `extra_holes`, and re-bake ground+amphibious on
   building placed/destroyed via `NavigationServer3D.region_set_navigation_mesh` on
   the retained region RIDs (`skirmish.gd:693-696`) behind a dirty flag +
   one-frame debounce. That call is **already used** at `terrain_builder.gd:541`,
   so this is an existing mechanism, not a new one.

**Gotchas:**
- `_build_ground_faces` blocks a cell on *any* overlap at `GRID_CELL = 4.0`, so a
  5×6 manufactory would carve ~8×8m. Use the existing `_cell_on_water_blob`
  (`:422`) centre-test trick, or a finer cell for building holes only.
- Re-path live units after a rebake or they walk into the new wall.
- If B5 landed first, slope rejection and building holes share one code path —
  sequence them so the second doesn't re-litigate the first.

**Verify:** order a unit straight across a manufactory, run 300 physics ticks,
assert it ends up past the building AND its path never entered the footprint AABB.
No unit inside a building AABB after 200 ticks. Screenshot of a unit routing around.

### C2. Real placement legality — *one session; needs B6*

`_placement_validity` (`skirmish.gd:1177`) passes only the **centre point** to
`is_position_blocked`, so a 10-deep heavy manufactory can overhang water/rock.
Adopt OpenRA's `CanPlaceBuilding = Tiles.All(IsCellBuildable)` semantics: sample
the whole footprint (~2m lattice over the XZ rect, all samples must pass), plus map
bounds, resource-node exclusion, and slope (now meaningful post-B5 — no building on
a cliff face, matching OpenRA's "buildings never on ramps" rule).

Dedupe the costs while here — `skirmish.gd:994-1007` hardcodes them as string
literals duplicating `building.gd:12 PREFAB_STATS`. Two sources of truth today.

On placement over your own units, shove them (OpenRA's `ClearBlockersOrders`)
rather than failing the placement.

**Simplify vs OpenRA:** no char-grid footprints, no `=`/`+` passable tiles, no
`BuildingInfluence` layer, no per-tile green/red grid. Continuous AABBs and one
ghost box are enough in continuous 3D.

### C3. Buildable area / adjacency — *afternoon; needs C2*

Replace "within 28m of any friendly building" (`skirmish.gd:1202`) with
`gives_buildable_area` / `requires_buildable_area` + per-kind `adjacent_m`,
measured **footprint-to-footprint** (expanded-AABB gap), not centre-to-centre —
the substance of OpenRA's `IsCloseEnoughToBase`. Default `adjacent_m = 8.0` ≈ RA's
`Adjacent: 2`; defences ~28m (RA's long-range class uses 7). Render the union as a
translucent ground decal so the rule is visible instead of guessed at.
**Skip** the radial `BaseProvider` mechanism — it exists for mission scripting.

### C4. Exits and rally points — *one session; needs A1, C1*

`building.gd:333` uses a fixed `Vector3(0, 0.5, footprint.z/2 + 3)` with **no
`terrain_height_at()` snap**, unlike `skirmish.gd:824` — which gets worse once
terrain is genuinely hilly. Replace with per-kind `exit_offset`/`exit_facing` in
`PREFAB_STATS`, height-snapped.

Add blocked-exit detection following OpenRA: if the exit volume is occupied, keep
the item `done` and **retry next tick**, and send occupying units a
`notify_blocker(exit_pos)` nudge — their `NotifyBlocker`/`INotifyBlockingMove`,
minus the cell abstraction. Settable rally point: select a manufactory, right-click
ground (replaces `building.gd:168`'s hardcoded ±10 z).

**Verify:** park 4 units on the exit, complete a job, assert the item stays `done`,
blockers move aside, unit eventually spawns.

## Phase D — Production depth

### D1. Drip-fed cost, pause-on-broke, refunds — *one session; needs A1, A2*

Adopt `ProductionItem.Tick` semantics directly:

```
expected_remaining = total_cost * remaining_time / max(1, total_time)
cost_this_tick     = remaining_cost - expected_remaining
if not spend(cost_this_tick): return    # NO progress this tick — pause, not slowdown
remaining_cost -= cost_this_tick; remaining_time -= 1
```

Cost here is metal+crystal, so charge each proportionally and require both. Latch
`total_time` at start (losing a factory mid-build doesn't retroactively change an
in-progress item — matches OpenRA). Refund is exact-progress:
`total_cost - remaining_cost`. Add `cancel(tier, index)` / `set_paused(tier)`.

**Tests must explicitly disable the A2 infinite-resources toggle** — otherwise
every assertion here passes vacuously.

**Simplify:** no `Infinite`/looping items, no 30s notification throttle — one
`_flash_status` on first stall.

**Verify:** 100 metal banked, queue a 300-cost unit, tick 200 physics frames —
progress stops partway, resumes on income, completes. Cancel mid-build refunds
exactly what was drawn (assert bank delta, not a formula).

**Gotcha:** `spend()` calls `_update_resource_ui()` every call — now once per
physics tick per queue. Add a dirty flag.

### D2. Queue HUD + categorised build bar — *one session; needs D1*

Replace the flat `ScrollContainer` (`skirmish.gd:981-1017`, mixing 5 building
buttons with up to 12 unit entries) with tabs: Structures / Defenses / Units. Add a
queue panel: three tier strips with progress fill and `READY`/`HOLD`/timer text,
computed OpenRA-style (`waiting = not producing and not done`). Left-click queues
(shift = 5), **right-click pauses, second right-click cancels**. Grey buttons when
no manufactory of that tier is alive — currently only a status flash (`:1084`).

**Verify:** non-headless script in `prototype/scratch/` driving real
`InputEventMouseButton` through tabs and right-click pause/cancel. This class of
bug is invisible to the headless suite — the wheels rebuild learned that the hard
way.

### D3. Multi-factory speed bonus — *afternoon; needs A1*

`build_time_speed_reduction = [100, 75, 60, 50]` (RA's *vehicle* table — every unit
here is a vehicle), indexed by count of live manufactories of that tier.
`total_time` stays latched.

**Verify:** 2 heavy manufactories → 0.75× time; destroying one mid-job leaves the
in-progress timer alone.

### D4. Buildings get build time — *multi-session; needs D1*

A fourth `structures` queue in the same drip-fed object. Adopt RA's "buildings
never auto-exit": clicking a structure button *enqueues* it; on `done` the button
reads READY and *then* `_begin_placement` runs. Placement spawns the node with a
`build_incomplete` flag for ~2s (scale-up tween), weapons/production/energy
contribution disabled until it clears — OpenRA gates this with a
`build-incomplete` condition on the building's other traits.

## Phase E — Systems that gate the rest

### E1. Real power states — *one session; needs D1, D4*

`_recalc_energy_economy` (`skirmish.gd:234`) derives OpenRA's three states:
`provided >= drained → Normal`; `provided > drained/2 → Low`; else `Critical`.
Replace the `build_time *= 1.5` hack (`skirmish.gd:1095` and its now-deleted AI
twin) with RA's tick-skip using `low_power_modifier = 300` (RA's own value, 3×
build time). Note OpenRA treats Low and Critical *identically* for production — the
distinction only drives conditions. Add a `low_power` flag disabling defence
weapons and dimming their mesh. HUD gets a real power bar rather than `:1062`'s
single text string.

### E2. Sell + repair — *afternoon; needs C2*

`refund = sell_value * 50% * hp/max_hp` (RA's `RefundPercent = 50`, health-scaled).
Repair on a 24-tick interval, 7 HP per step,
`cost = hp_to_repair * 20% * value / (max_hp * 100)`, min 1. **Skip** the
multi-repairer `RepairBonuses` table — single-player, no allied repair race.

### E3. Tech-tree greying + cancel-unbuildable — *one session; needs D2*

Per-team owned-kind counts, rebuilt on building added/died; palette greys/hides.
`cancel_unbuildable_items()` refunds queued items whose tier manufactory just died
— OpenRA's `CancelUnbuildableItems`, which is what makes "lose your refinery, lose
your queue" feel fair rather than silently broken. **Skip** the prerequisite string
DSL (`!name`, `~name`) — this game's only real prerequisite is tier → manufactory.

## Explicitly out of scope

Not worth porting to a solo hobby prototype in continuous 3D:

- **Per-cell resource density layers + `CustomTerrain`** — no cell grid; discrete
  resource nodes are strictly better here. (Resource *regrowth* is still worth
  having eventually — adopt `SeedsResource`'s random-walk semantics against
  discrete nodes, not a density layer.)
- **The tileset indirection** — a global terrain table for a handful of maps is
  ceremony; B4's per-map surface map already wins.
- **`cost = 10000/speed` pathing** — Godot has no per-face cost. The existing
  4-navmesh split (ground/water/amphibious/deep_water) *is* the locomotor
  abstraction; keep RA's speed table as a balance reference only.
- `MapSize`/`Bounds` duality; `Uid` SHA1 (no multiplayer); Lua scripting + layered
  rules overrides; a full in-engine map editor (ship the Python generator +
  `scratch/capture_map.gd` + B9's baked preview instead).
- Infinite/looping build items; `BaseProvider`; char-grid footprints, bibs,
  `BuildingInfluence`; multiple prioritised exits with `ExitDelay`;
  MCV/`Transforms` deploy; client-vs-server placement re-validation; fake
  buildings; capture/engineers; wall segments.

## Verification conventions (every chunk)

```bash
cd prototype && ./Godot_v4.3-stable_win64_console.exe --headless --script run_tests.gd --path .
```

Expect exit 0 and `ALL AUTOMATED TESTS PASSED SUCCESSFULLY!`. Notes:
- One genuinely flaky test exists (an AI-kiting standoff-distance check) — **rerun
  once** before treating a failure there as real.
- Headless spams `ERROR: Parameter "m" is null. at: mesh_get_surface_count` —
  pre-existing harmless noise from the dummy renderer.
- Some verification **must** run non-headless (real viewport); input/drag bugs are
  invisible otherwise. Put those in `prototype/scratch/`.

Per project convention each chunk ships with: new tests in `run_tests.gd`,
screenshots under `prototype/progress_captures/<date>/<feature>/`, a `PROGRESS.md`
entry, and judgment calls logged in `DECISIONS_NEEDED.md`. Favour **behavioral**
proofs (real spawned units, real physics ticks, real path-connectivity, pixel
readback) over catalog-number assertions.
