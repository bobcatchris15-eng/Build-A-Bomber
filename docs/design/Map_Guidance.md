# Map Guidance — Marshes & Island Hopping

> **Purpose.** The current roster is 10 flat, mostly-dry maps where water is an
> occasional obstacle and the ground is one big continuous sheet. This document
> records how *other RTS games actually built* marsh and island-hopping maps,
> and — more importantly — how to translate those patterns onto **this project's
> concrete map system** (JSON definitions → 4 baked navigation surfaces →
> per-locomotion terrain speed). It is a design guide for authoring new maps,
> not a promise that every mechanic below exists in code today. Where a pattern
> needs a code change, this says so explicitly and points at the file/roadmap
> section it would touch.

---

## 1. How maps work in this project today (the ground truth)

Everything a map *is* lives in one JSON file under `res://data/maps/*.json`,
validated and decoded by `scripts/map_catalog.gd` (schema: `FIELD_SPEC`),
then turned into terrain by `scripts/terrain_builder.gd` and
`scripts/skirmish.gd`. Authoring a map = writing JSON. There is no editor,
no tileset, no map binary format.

### 1.1 The schema fields (what you can write)

| Field | Shape | What it becomes |
|---|---|---|
| `name`, `description` | string | Shown in `map_select.gd`'s list. The description is the map's pitch to the player. |
| `map_half_extents` | number | The map is a square from `-half` to `+half` on X and Z. `lake_crossing`=240, `twin_bridges`=300, `scattered_peaks`=550. |
| `ground_color` | RGB | Base ground tint before surface zones. |
| `water_blobs` | `{center, radius, irregularity?, depth?, shore_blend?}` | Circular water with wobbly edges (`irregularity`) and soft shores (`shore_blend`). Good for ponds and marsh puddles. |
| `water_areas` | `{center, half_extents}` | Rectangular water. **Feeds the naval navmesh** — naval units float here. |
| `shallow_water_areas` | `{center, half_extents}` | A shallower band of the same water, drawn inset from the open water. |
| `obstacles` | `{center, half_extents, type: "rock"/"building", building_height?}` | Static bodies that block movement **and** LOS. Rocks and buildings are both cover. |
| `surface_zones` | `{center, half_extents, surface_type}` | Painted ground type (`marsh`, `rocky`, `snow_mud`, `sand`, `gravel`, `forest`, `ice`). **These are real gameplay, not paint** — see §1.3. |
| `bridges` | `{center, half_extents, deck_height?}` | A dry strip carved through a `water_areas` hole, walkable by ground/legged units only. Naval units still sail underneath. |
| `resource_nodes` | `{position, type: "metal"/"crystal", amount}` | Harvestable nodes. |
| `spawns` | `[{id, hq, factory, refinery, harvester}]` | Player/enemy starts. Today every map authors exactly two: `"player"` and `"enemy"`. |
| `terrain.features` | `[{type: hill/basin/plateau/ridge/ravine/escarpment/cliff, ...}]` | Real elevation, generated by `tools/terrain/build_terrain.py` into a heightmap + surfacemap PNG. **Only `scattered_peaks` uses this today.** |

### 1.2 Four navigation surfaces — the key to marsh & island maps

`terrain_builder.gd` bakes **four independent navmeshes**, and which units use
which is what makes a map play the way it does:

| Navmesh | What's walkable | Who uses it |
|---|---|---|
| **ground** | Dry land, minus water/obstacle/bridge-carve footprints | Wheels, treads, legs, half-tracks, rocker-bogies, anti-grav, pontoon-wheel |
| **amphibious** | Dry land **plus** water | Screw-drive (amphibious augers), and any amphibious unit |
| **water** | `water_areas` footprints only | Shallow-draught naval hulls |
| **deep_water** | The deeper interior of the same water | Deep-draught naval hulls (cruisers stay further out) |

So a marsh that's *crossable but slow* is fundamentally different from a lake
that's *impassable*. A marsh can be pure ground (all locomotions cross it, at a
penalty), which keeps the map one big connected ground navmesh. Water, by
contrast, *disconnects* the ground navmesh — islands only stay connected via
bridges (ground) or amphibious units (everything).

### 1.3 Terrain types have teeth (the marsh data)

`scripts/module_catalog.gd` — `TERRAIN_SPEED_MULTIPLIERS` — multiplies every
locomotion type's speed per surface type. **Marsh is the most punishing
non-naval terrain in the game** for wheels, and a *bonus* for hover/air-cushion:

| Locomotion | Marsh | Rocky | Snow/Mud | Sand | Gravel |
|---|---|---|---|---|---|
| wheels | **0.25** | 0.35 | 0.20 | 0.30 | 1.25 |
| tracked_treads | 0.45 | 0.75 | 0.80 | 0.85 | 1.10 |
| legs | 0.60 | 1.10 | 0.75 | 0.80 | 1.02 |
| screw_drive | **1.10** | 0.50 | 0.70 | 0.60 | 1.00 |
| hover_engine | **1.15** | 0.55 | 1.10 | 1.15 | 0.95 |
| air_cushion_skirt | **1.20** | 0.40 | 1.15 | 1.10 | 0.85 |
| anti_grav_plate | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 |
| pontoon_wheels | 0.90 | 0.35 | 0.50 | 0.45 | 1.05 |

Design implication, from the data: **a marsh-heavy map is a map where
screw-drive, hover, and air-cushion units are the *good* ground units, and
wheeled vehicles are a liability.** That's a real rock/paper/scissors lever —
the game already has the mechanic, no map ever leans on it hard.

**Beyond speed — what other RTS games do with marsh terrain** (research from
AoE2, SC2, CoH, DoW, SupCom, TA):

| Mechanic | Source | How it translates to this project |
|---|---|---|
| **Concealment** (marsh hides units, LOS penalty) | DoW tall grass, SC2 creep | Pair marsh zones with `obstacles` type `"building"` (reeds/trees) — they already block LOS. No code change needed. |
| **Acid / damage over time** | SC2 Bel'Shir pools | New `surface_type: "acid_marsh"` in `FIELD_SPEC` enum + `TERRAIN_SPEED_MULTIPLIERS` entry + per-tick DPS in `battle_unit.gd`. 5 DPS to non-`corrosion_proof` units, 2× crystal spawn rate as reward for risk. |
| **Submerged stealth** | SupCom subs invisible to radar, visible to sonar | Amphibious units in water >1.5m depth: `fog_hidden=true`. Requires `skirmish.gd` LOS check to consult navmesh depth at unit position — small code addition. |
| **Bog-down / capture** | CoH mud immobilizes vehicles; engineers can salvage | Units >120% weight ratio in marsh: 10%/sec immobilize chance. Capturable by `salvage_beam` engineer module. Needs `battle_unit.gd` weight check + new `salvage_beam` interaction. |
| **Dynamic marsh spread** | WC3 blight expands from structures | Faction ability: structures spread `surface_type: "marsh"` in 30m radius over 5 min. Counter: `terraforming_drone` module. Design-only, no terrain_builder.gd change. |
| **Vision penalty** | SC/DoW marsh/forest reduces sight range | `vision_range *= 0.7` for marsh; `*= 0.5` for acid_marsh; `sensor_suite` module mitigates +15%/module. Small addition to `battle_unit.gd`'s vision calc. |
| **Marsh-water blob mixing** | TA/SC wetlands = marsh + water intermixed | `surface_zones` with embedded `water_blobs` — the existing schema already supports this. A marsh zone can overlap a water_blob zone; the water wins for navmesh, marsh wins for surface type. No code change. |

### 1.4 The fairness lint (what a new map must pass)

`MapCatalog.lint_spawn_fairness()` runs on every map at load/smoke-test. A new
marsh or island map **must** pass all of:

- ≥ 2 spawns, with HQ pads on **legal ground** (not blocked terrain).
- ≥ `FAIRNESS_MIN_RESOURCES_PER_SPAWN` (2) resource nodes within
  `0.6 × map_half_extents` of each HQ.
- **All spawns mutually reachable on the *ground* navmesh** — this is the
  constraint that bites island maps. Two islands connected only by water fail
  the ground-reachability lint *unless* there's a bridge. Reachability is
  measured with a 12-unit margin (a building carves its own navmesh hole).
- Pairwise spawn distances don't vary too much (coefficient of variation ≤ 0.35).

There is no automatic lint for "spawn is on the same landmass as the map
center" — a map can pass all four checks while being trivially enclosed, so
authoring judgment still matters.

## 2. How other RTS games actually do marsh maps

*(This section distills the web research; see §6 for sources.)*

**Age of Empires 2 — "Swamp" / wetland maps.** Marsh is treated as *slow
ground, not water*. Units path across it at reduced speed rather than being
blocked, which means a swamp is a **soft chokepoint** — you can push through,
but it takes long enough that the defender reacts. Aoe2 also models "fordable
water": a shallow band across a river that units can wade at a speed penalty,
creating a third crossing option beyond "bridge" and "long way around." The
design lesson: **don't make marsh impassable; make it expensive.** Impassable
marsh is just a lake with a skin. Expensive marsh creates decisions.

**Total Annihilation / Supreme Commander — wetlands.** T.A. has real terrain
height and water *depth*; marsh sits between walkable and deep-water, and
amphibious units are a first-class answer. The lesson carried into this
project's own design already: `screw_drive` exists specifically to cross water
*and* marsh at full speed (§1.3). SupCom's marsh maps also prove the value of
**mixed terrain density** — pockets of marsh rather than one giant swamp, so
there are dry fast-lanes through the map.

**StarCraft — "creep"/high-ground interplay.** StarCraft's muddy maps use
concealment and vision more than speed: terrain that *hides* units is as
powerful as terrain that *slows* them. In this project, that role is played by
`obstacles` (they block LOS, per `map_catalog.gd`'s header) — so a marsh map
can pair slow ground with LOS-blocking reeds/trees to make it genuinely
dangerous to push blind.

**Company of Heroes — mud slows and pins.** CoH models mud as a *tactical
slow* with combat consequences, not just travel. The transferable idea: marsh
is a place you don't want to fight in, because your units arrive slowly and
arrive separated.

### Marsh patterns that map cleanly onto this project

1. **Marsh = surface_zones, not water.** Paint `surface_type: "marsh"` over
   big areas. Ground navmesh stays continuous (no connectivity break), and the
   speed multipliers in §1.3 do all the work. This is *free* — the mechanic
   exists, no map uses it as a centerpiece.
2. **Marsh pockets around water_areas** (the T.A./Aoe2 mixed-density lesson).
   Put a `water_blob` or `water_areas` hole, ring it with marsh, keep dry
   fast-lanes between the pockets. Naval units get their lane; hover units get
   a full-speed lane; wheeled units get a slow flanking route; screw-drive is
   king.
3. **Fordable water.** `shallow_water_areas` already exists in the schema but
   no map uses it for crossing. A wide shallow band across a `water_areas`
   river, plus an amphibious navmesh that crosses it, is Aoe2's ford exactly.
4. **Marshy spawns.** A marsh map can put one spawn's economy on firm ground
   and the *contested* center in the marsh — so the fight happens in the slow
   zone, which is where hover/air-cushion factions want it.

## 3. Island hopping / archipelago maps

### How the classics do it

**Supreme Commander — "Seton's Clutch" (the canonical island map).** Six-ish
players, each on their own island, connected by a few land bridges and open
water. The famous dynamic: *naval is mandatory, air is king, and the bridges
are fought over*. SupCom shows the core archipelago truth — **islands make the
map about *who controls the connectors*, not the open ground.** Because every
naval path converges on a few straits, naval dominance is decided in a handful
of fights, not across a front line.

**Age of Empires 2 — "Islands" / "Nomad".** Each player starts alone on an
island with a transport. The map is defined by *early transport micro* and the
decision of when to go to sea. Aoe2 islands are **sparse** — big islands, few
of them, so land is genuinely scarce and worth fighting over.

**Total Annihilation — archipelago with bridges.** T.A. mixes real islands with
a few deliberate land bridges, so ground armies can still reach each other but
every crossing is a funnel. This is the pattern that survives this project's
ground-reachability lint (§1.4): the islands are *connected by bridges*, which
the schema already supports and `twin_bridges` already demonstrates.

### Island patterns that map cleanly onto this project

1. **Islands = water_areas walls + bridges.** The schema has both. An
   archipelago is just `water_areas` polygons carved around `obstacles`-free
   landmasses, joined by `bridges`. The ground navmesh stays connected through
   the bridges (lint passes), naval units sail the channels (the water navmesh),
   amphibious units ignore the bridges entirely (the amphibious navmesh).
2. **Deep-water channels for naval play.** `water_areas` + `shallow_water_areas`
   give you deep straits and shallow landing zones — naval hulls that need deep
   water are confined to the main channels, shallow-draught boats and
   amphibious units can beach. That's the coastal_strand mechanic, scaled up to
   whole-map geometry.
3. **Spawn fairness is the hard part.** Every spawn must have ≥2 resources in
   radius *and* be ground-reachable from every other spawn. Author islands so
   each has its own economy (metal + crystal on-island) and at least one bridge
   link to the wider world. The biggest trap: a spawn on a tiny island that can
   be starved out because its bridge is destroyed. Give every island two links
   where possible.
4. **Resource distribution.** The SupCom lesson is to keep contested resources
   *between* islands (on the small mid-islands or the bridgeheads) rather than
   inside each player's home island, so the map produces fights instead of
   turtling.

**Island size thresholds** (from AoE2 + SupCom research, in Godot units = 1m):

| Category | Radius | Supports | Min Navmesh Nodes |
|---|---|---|---|
| Micro-atoll | 25–40m | Single mex/well, radar, 1 turret | ~50 |
| Outpost | 50–80m | 1 factory + 3 mex + defenses | ~200 |
| Standard Spawn | 100–150m | Full T1 base, 6–8 mex, airpad | ~800 |
| Main/Capital | 200–300m | Multi-player, T2/T3, nuke defense | ~2500 |

**Rule**: Spawn island ≥ 120m radius for vehicle-building RTS (chassis + turret factories + resource processors).

**Naval vs air vs ground crossover points** (your locomotion types map directly):

| Tech Stage | Dominant Crossing | Counters | Your Locomotion |
|---|---|---|---|
| **Early (T1)** | Naval (gunboats, torpedo boats) | Subs, torpedo bombers, coastal artillery | Naval hulls, screw-drive amphibious |
| **Mid (T2)** | Air transports + hover/amphibious | AA ships, fighters, long-range artillery | Hover (ignores water), screw-drive |
| **Late (T3)** | Strategic air + experimentals | Heavy AA, fighters, nuke/anti-nuke | Air (bypasses all water) |
| **Endgame** | Teleport / orbital / superweapons | Counter-superweapons, map control | All |

**Transport/bridge mechanics** (already in the schema, worth calling out):

| Crossing Method | Navmesh Used | Tech Tier | Capacity | Vulnerability |
|---|---|---|---|---|
| Naval transport | water_map | T1 | 8–12 units | Subs, torpedoes, air |
| Amphibious (screw/hover) | amphibious_map | T1–T2 | Unlimited (unit speed) | Slow, coastal artillery |
| Air transport | N/A (flying) | T2 | 6–10 units | Fighters, AA |
| Bridges (buildable) | ground_map | T2 | Unlimited | Destroyable, static |
| Hover ferry | amphibious_map | T2 | 15–20 units | AA, artillery |
| Submersible transport | deep_water_map | T3 | 4–6 heavy units | Sonar, depth charges |

Bridges are already implemented — engineer-placed rectangular walkable strips carved through water holes. Dynamic navmesh recalc on placement works because `terrain_builder.gd` already supports mid-match rebake (`rebake_ground_and_amphibious_async()`).

## 4. Godot 4 implementation notes specific to this project

### 4.1 The 4-navmesh system already gives you both map types for free

The engine-side machinery for marsh *and* island maps **already exists**. The
gap is purely content (new JSON) plus, for the most interesting variants, a
couple of small code touches listed in §5. There is no HeightmapTerrain plugin
or terrain-shader work needed for either archetype.

**Deliberate verdict: do NOT adopt a heightmap-terrain plugin (e.g. Zylann's
HTerrain).** The existing `terrain_builder.gd` stack is a better fit for an RTS
than any painting plugin: one deterministic `height_at()` shared by the
navmesh bake, the visuals, gameplay Y-snap, and LOS; four layerable
NavigationServer3D maps with async rebaking; and organic water blobs that drive
navmesh holes, visuals, and shore terrain dip simultaneously. HTerrain offers
LOD/editor painting but has zero water-body handling and none of the
deterministic shared-height guarantees this project depends on. Adding it would
be a lateral move at best, a regression at worst.

**Your 4-map architecture matches Godot docs exactly** — *"Use distinct
NavigationServer3D maps for wholly separate areas / islands"* — and the
research agent confirmed this is the canonical Godot pattern for archipelago maps.
Each island = disjoint region on the same `ground_map`; water between =
`water_map` + `deep_water_map`; amphibious units query `amphibious_map`.

### 4.2 Big-map gotchas to remember (from `terrain_builder.gd`)

- **Recast segfaults on huge grids.** Beyond ~300 half-extent,
  `_nav_cell_size()` widens the voxel cell (`terrain_builder.gd`), and
  `_nav_grid_cell()` widens the grid cell, to keep triangle counts bounded.
  Island maps want *more geometry per unit area* (many shorelines), so keep
  half-extent modest (240–300) unless you specifically need the space.
- **Every shoreline is geometry.** Each `water_areas` rect and `water_blob`
  adds shoreline. An archipelago with 20 islands is 20× the shoreline detail of
  one lake. If bake times regress, prefer fewer, larger islands over many tiny
  ones, and reuse `_nav_cell_size()`'s existing scaling rather than raising
  `GRID_CELL` (the file's own notes record that widening the cell broke pathing).
- **Bridges don't remove water from the naval maps.** A bridge carves dry land
  only from the *ground* navmesh; naval units sail under it. That's correct for
  island maps — a bridge is a land connector that doesn't seal the channel.
- **Surface zones never appear in the navmesh holes** (`_collect_holes()`).
  Marsh is walkable-by-all *by construction*; only `water_*` and `obstacles`
  carve navmesh. So a marsh map is, navmesh-wise, a flat dry map with paint —
  cheap to build and cheap to rebake.
- **`lint_spawn_fairness` needs a real baked ground navmesh RID.** It calls
  `NavigationServer3D.map_get_path()` on the *ground* map. Author islands with
  bridges *first*, bake, then check the lint before polishing.

**Navmesh tuning constants to add for marsh/island density** (in
`_bake_nav_mesh()`):
```gdscript
nav_mesh.region_min_size = 8.0      # discard micro-regions from tiny holes
nav_mesh.region_merge_size = 30.0   # merge small regions
nav_mesh.sample_partition_type = NavigationMesh.SAMPLE_PARTITION_MONOTONE
```
These keep the ground navmesh clean when dozens of small `water_blob` holes
exist, without changing cell size or breaking pathing.

**Water rendering priority fixes** (from Godot impl research):

| Fix | Effort | Impact |
|---|---|---|
| **Merge all water into ONE ArrayMesh** at spawn | 0.5 day | Eliminates N draw calls; biggest rendering win at 20+ water bodies |
| **Shoreline foam + depth blending** via distance-field shader | 2 days | Visual quality — replaces hard alpha edge with organic fade |
| **Single shared water material** — all uniforms global/wetness-map driven, no per-instance params | included in above | Reduces material binds |

**Merged water mesh** (pseudocode for `terrain_builder.gd`):
```gdscript
var st = SurfaceTool.new()
st.begin(Mesh.PRIMITIVE_TRIANGLES)
for w in map_def.water_areas:
    _append_water_quad(st, w)
for blob in map_def.water_blobs:
    st.append_from(Mesh, _blob_fan_mesh(blob), 0)
var water_mesh = ArrayMesh.new()
st.commit(water_mesh)
# Single MeshInstance3D, one shared material
```

**Water shader** — distance-field foam + depth color:
```glsl
// water_marsh.gdshader
uniform sampler2D wetness_map;  // distance transform from water edges
float shore_dist = texture(wetness_map, world_pos.xz * scale).r;
float foam = smoothstep(foam_start, foam_end, shore_dist) * (1.0 - depth);
alb = mix(deep_color, shallow_color, 1.0 - depth) + foam_color * foam;
```

**Additional gotchas** (from Godot impl research):
- **Water shadow acne**: disable shadow casting on water, or lower shadow priority
- **Transparent overdraw** (water + shallow marker): merged water mesh + fewer transparent layers helps
- **HeightMapShape3D perf**: `COLLISION_HEIGHTMAP_STEP=3.0` + node scale is good; consider 4.0 for marsh maps with many small blobs

### 4.3 Materials / appearance for marsh

Marsh already has albedo variants on disk (`TERRAIN_TEXTURE_DIR` +
`marsh_*_albedo.png`, selected in `terrain_builder.gd`'s
`_build_blended_surface_material()`). A marsh map is mostly just `marsh`
surface zones tinted with a dark `ground_color` underneath. If you want reeds/
cattails as LOS-blocking cover, that's the existing `obstacles` `type:"building"`
path (or a new `type:"reeds"` in the `FIELD_SPEC` enum — see §5).

**Marsh visual upgrade path** (from Godot impl research):
- Extend `tools/terrain/build_terrain.py` to output a **wetness map PNG** (16-bit
  distance transform from water edges) — same pipeline that generates
  heightmap/surfacemap.
- In `terrain_ground.gdshader` (marsh variant), sample wetness:
  ```glsl
  float wetness = texture(wetness_map, uv).r;
  ALBEDO = mix(dry_marsh, wet_marsh, wetness);
  ROUGHNESS = mix(dry_roughness, 0.1, wetness);  // wet = glossy
  ```
- Add a third "mudflat" albedo blended where `water_dist < 4-8` using the same
  wetness map. The variant system (`marsh_v1`/`v2`/`v3`) already supports this;
  just add the texture files.
- For LO-blocking reeds/cattails: author as `obstacles` with a new `"reeds"`
  enum value in `FIELD_SPEC` (one-line addition) + a mesh variant in
  `terrain_builder.gd`'s obstacle builder — not a new system.

### 4.4 Water depth as a soft crossing (the ford idea)

`shallow_water_areas` is a *visual* band today; the *mechanical* crossing
question is answered by the amphibious navmesh, which treats all water as
crossable. A ford is therefore achieved by: (a) `water_areas` river, (b)
`shallow_water_areas` band across it for looks, (c) amphibious units crossing
anywhere — which they already can. To make only *some* water fordable, you'd
need a shallows-only amphibious variant of the navmesh (a new `shallow_water_map`
baked from `shallow_water_areas`), which is a `terrain_builder.gd` addition, not
a map-JSON one.

**Water rendering upgrade** (from Godot impl research):
- **Merge all water into ONE ArrayMesh** at spawn (eliminates N draw calls for
  many water bodies): build a single `SurfaceTool` from all `water_areas` quads
  + `water_blob` fans, commit to one `ArrayMesh`, one `MeshInstance3D`, one
  shared material.
- **Shoreline foam + depth blending via distance field**: extend
  `build_terrain.py` to output a distance-from-water-edge map; sample in
  `water_marsh.gdshader`:
  ```glsl
  float shore_dist = texture(wetness_map, world_pos.xz * scale).r;
  float foam = smoothstep(foam_start, foam_end, shore_dist) * (1.0 - depth);
  alb = mix(deep_color, shallow_color, 1.0 - depth) + foam_color * foam;
  ```
- Keep **planar reflection only for the single largest water body** (costly);
  disable shadow casting on water to avoid shadow acne/wasted cascade resolution.

## 5. Concrete recommendations & new-map playbook

### 5.1 New maps to author (in this project's JSON schema)

**Marsh map A — "The Mire".** One big connected ground sheet; a large central
`water_blob` or `water_areas`; most of the map painted `marsh`, with dry
`gravel` fast-lanes (gravel is the *fastest* ground: wheels 1.25×) running from
each spawn toward the center and the enemy. Spawns on firm `sand`/bare ground.
Put the contested crystal node dead-center in the marsh where hover units have
the edge. This is 100% existing mechanics — no code changes, just JSON. It will
fail nothing in the lint (continuous ground, both spawns reachable).

**Marsh map B (needs one small change) — "Reed Bed".** Marsh A plus
LOS-blocking `obstacles` clusters (reeds) scattered through the marsh so
crossing it blind is dangerous. Uses the existing `type:"building"` obstacle as
cover — **no code change required** — or, if you want them to read as reeds
rather than buildings, add a `"reeds"` value to the `obstacles.type` enum in
`map_catalog.gd`'s `FIELD_SPEC` (one-line enum addition + a visual variant in
`terrain_builder.gd`'s obstacle mesh builder).

**Island map A — "Chain Islands".** A long diagonal chain of islands down the
center of a 240–300 map, flanked by open `water_areas`. Each island has its own
economy; islands are joined by `bridges`; the two spawns sit on the end
islands, each with ≥2 resources in radius and a bridge link toward the middle.
Players must fight *along* the chain — the SupCom connector-control dynamic.
All existing mechanics; the lint passes because the chain keeps the ground
navmesh connected.

**Island map B (needs `deep_water` authored) — "Shattered Sea".** Larger map,
a few big islands, wide deep-water channels between them so heavy naval hulls
rule the open water and only shallow-draught boats/amphibious can beach. Uses
`water_areas` for the channel + `shallow_water_areas` for the beach shelf —
both fields exist, no map in the roster has combined them at this scale yet.

### 5.2 Checklist every new map must pass before it ships

- [ ] `map_catalog.gd` loads it with no validation errors (run the test suite /
      a smoke test that calls `get_map(id)`).
- [ ] Every spawn's HQ is on legal, unblocked ground.
- [ ] Every spawn has ≥2 resource nodes within `0.6 × half` of its HQ.

## 6. JSON Map Definition Recommendations

### 6.1 Current Schema Analysis

Your existing schema (`map_catalog.gd:307-378`) already supports:
- `water_blobs` — organic lakes with irregularity, depth, shore_blend
- `water_areas` — rectangular water
- `shallow_water_areas` — shallow-draught-only zones
- `surface_zones` — 8 types including marsh, rocky, snow_mud, sand, gravel, forest, ice
- `bridges` — rectangular walkable strips
- `terrain` — heightmap + surfacemap + features (hill/basin/plateau/ridge/ravine/escarpment/cliff)
- `obstacles` — rocks/buildings
- `resource_nodes` — metal/crystal with amounts
- `spawns` — N-player with id, hq, factory, refinery, harvester

## 9. Open questions for the next map-authoring session

1. Should a marsh map give hover/air-cushion units a *sight* advantage, or keep
   it purely movement-speed? (Current code: movement only.)
2. Should the island maps allow spawns on *different* islands, or always keep
   spawns ground-reachable by bridge (the lint's requirement today)? Relaxing
   it would enable Aoe2-style isolated starts but needs a new spawn-fairness
   rule ("has a transport/bridge within X").
3. Do we want `deep_water` to be a *separate JSON field* (like
   `shallow_water_areas`) instead of being derived from `water_areas`? Today a
   map author can't say "this channel is deep, that one is fordable" — the
   distinction is implied by `shallow_water_areas` insets.
